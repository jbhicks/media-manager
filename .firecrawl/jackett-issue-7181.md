I want my jackett client to select which configured scrapers should be used. In theory, this would work by simply calling `api/v2.0/indexers?configured=true` initially and then call each indexer endpoint based on the users preference. However, when an admin password is set, `api/v2.0/indexers?configured=true` does not work with API Keys. It requires manual cookie-based login.

**Solution**

One solution is to allow API access with two login methods:

- Cookie Login (UI, Browser)
- API-Key (APIs, Mobile API)

However, this would mean **everyone who has the API-Key can control the Jacket instance**, which does also not sound good/promising.

So what would you guys suggest? _IMO_ it would be nice for clients to know what indexers jackett currently supports, pros:

- The user does not have to manually copy every indexer over.
- You can keep them up-to-date/manage without user interaction
- Clients can disable on a indexer basis

Thoughts?

Jackett has 2 types of APIs:

- External APIs Torznab, CouchPotato, RSS with well defined formats that never change and the authorization is via API-key
- Internal APIs used by the Jackett UI. These APIs can change at any time without notification and you need the Password or the Cookie to interact.

I think we should provide more external APIs to be used by third party apps. That will allow native Jackett clients with more features. But that APIs have to be well defined, documented, versioned and be stable enough. We are not working in this ATM, but it's interesting.

Yes, and there also needs to be thoughts about securing that API. Right now, an API Key can only be used for scraping while the admin password also allows management of the scrapers. Now. if there is an API which allows to do both in the same interface, there is maybe a need for API-Keys with different permissions like `read` and `write`.
